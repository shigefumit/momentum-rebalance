## いま使うもの: モメンタム・リバランス

### ルール

> **毎月1回、丸1年前の終値と比べて最も上がっていた5銘柄を等ウェイトで持つ。それだけ。**

測定は**カレンダー基準**です。8月1日に入れ替えるなら、前年8月1日相当の終値から
7月末終値までを比べ、上位5銘柄に8月1日に乗り換えます。
`momentum.py --asof 2026-07-31` で過去の任意日の判定を再現できます。

損切りなし。指値なし。チャート分析なし。AIなし。**タイミング判定なし。**

### 検証結果（配当込み・売買コスト0.2%・譲渡益税20.315% 反映後）

| | 2006〜2015年 | 2016〜2026年 |
|---|---|---|
| **このルール** | **+460%** | **+1,951%** |
| 全銘柄を持ち続けた場合 | +174% | +1,308% |
| 最大の落ち込み | −57% | −41% |

リーマンショックを含む10年とAI相場の10年、**両方で「何もしない」を上回りました。**

### アプリ

## → **https://shigefumit.github.io/momentum-rebalance/**

Safariで開いて「共有 → ホーム画面に追加」でアプリになります。ログイン不要。

**できること**

- **現在の評価額**を表示（現金＋保有株の時価）。資産が増減すればそれに追随します
- 銘柄ごとの**株数・取得単価・現在値・損益**
- **今月の発注内容**を株数まで計算。「◯◯を12株売る」「◯◯を8株買う」の形で出ます
- 「この通り発注した」を押すと保有を記録。翌月は差分だけ出ます
- 実際の約定が推奨と違った場合の**手動修正**
- 保有する銘柄数を 3 / 5 / 10 で切り替え（それぞれの検証上のリスクも表示）

株数は**その時点の評価額**を基準に計算します。300万円が600万円になれば、
1銘柄あたりの予算も倍になり、買う株数も増えます。

保有情報はブラウザ内（localStorage）にのみ保存され、サーバーには送られません。
そのため**他の閲覧者にあなたの保有は見えません**。通信を一切行わないので
オフラインでも開けます。

### 毎月の更新手順

```bash
.venv/bin/python momentum.py --json app_data.json   # 最新の順位を計算
.venv/bin/python build_app.py                       # app.html と docs/index.html を再生成
git add -A && git commit -m "$(date +%Y-%m) の順位を更新" && git push
```

プッシュから1〜2分でGitHub Pagesに反映されます。

CLIだけで済ませる場合:

```bash
.venv/bin/python momentum.py                        # 今月の判定を表示
.venv/bin/python momentum.py --top 3                # 上位3銘柄版
.venv/bin/python momentum.py --set MU INTC AMD LRCX AMAT   # 保有を登録
```

### このルールについて必ず覚えておくこと

1. **月1回だけ実行する。** 頻繁に見ても意味がなく、売買が増えて手数料と税金だけが増えます
2. **タイミングを足さない。** 「相場が悪いから今月は現金で」をやると検証では
   +1,951% → +636% に落ちました。後知恵で勝ち組を選んだ場合でも
   +11,208% → +1,579% に落ちています。**悪手だと数字で分かっている操作です**
3. **途中で資産が半分近くになる。** 最大 −57%。300万円が129万円に見える時期を
   持ち続けられるかが成否をすべて決めます
4. **セクター分散されない。** 上位が同一セクターに固まることがあります
   （2026年7月は5銘柄すべて半導体）。アプリが警告を出します
5. **検証は今も上場している銘柄のみ。** この20年で潰れた会社は入っていないため、
   実際の成績はこれより悪くなります
6. **「モメンタム効果」として学術的に知られた現象で、私の発明ではありません。**
   同時に壊滅的に失敗する時期があることも知られています（有名なのは2009年）

## 検証の記録

**[FINDINGS.md](FINDINGS.md)** に全数値と再現手順があります。設計の経緯は [PLAN.md](PLAN.md)。

### 何が起きたか

1. **Phase 0** — テクニカル指標で「買う／売る／何もしない」を判定するエンジンを作った
2. **Phase 1** — 10年分でバックテスト。**期待値 −0.134R で負けた**（総リターン −23.1%）
3. **診断** — 決済ロジックを切り離して測定し、3つの構造的欠陥を特定
   - 損切りがノイズの内側（MAE中央値 −1.54R に対し損切り −1.0R。63%が上がる前に振り落とされていた）
   - 「+1Rで半分売却＋建値撤退」が勝ちを +0.5R に切り詰めていた
   - 200日線決済が損失源（31件 −0.584R）
4. **Phase 1b** — 期間分割で修正版を検証。**期待値 +0.339R に反転し、検証期間でも維持**。
   仮説の順位が開発期間と検証期間で完全一致（＝当てはめではない）。
   セクターETFという別ユニバースでも +0.297R で再現
5. **しかし** — 市場滞在率が19〜40%しかなく、資本の8割が遊ぶため
   バイ&ホールドに届かなかった（+40.5% vs +147.6%）
6. **Phase 2** — 「後知恵でもいいから勝てるルールを探す」に方針転換。
   結果、**後知恵を必要としないモメンタム・ルール**が両期間で勝つことを発見

### 一番大きな学び

> **勝敗を決めていたのは「いつ買うか」ではなく「何を持っているか」だった。**

Phase 0〜1b で作ったのは「いつ買うか」を当てるツールでした。負けた理由がこれです。
後知恵で勝ち組を選んでも、そこにタイミング判定を足すと +11,208% → +1,579% に落ちました。

**実損はゼロです。** 発注する前に検証しました。

## ファイル構成

### いま使うもの

| ファイル | 役割 |
|---|---|
| `momentum.py` | モメンタム判定（本番）。順位・株数・乗り換え指示を出す |
| `app_template.html` | アプリの画面。ここを編集すると見た目と挙動が変わる |
| `build_app.py` | テンプレートにデータを埋め込んでHTMLを生成 |
| `app.html` `docs/index.html` | 生成されたアプリ本体 |
| `research.py` | 戦略ラボ。ズルの段階を分けて総当たり比較 |
| `config.py` | 全パラメータ |
| `fetcher.py` | データ取得層（キャッシュ・レート制限対策・配当込み株価） |

### 検証に使ったもの（記録として保持）

| ファイル | 役割 |
|---|---|
| `backtest.py` | トレード単位のバックテスト（Phase 1） |
| `diagnose.py` | 原因の切り分け（MAE/MFE分析・フォワードリターン対ベースライン） |
| `validate.py` | 期間分割検証（Phase 1b） |
| `rules.py` | テクニカル判定ルール |
| `indicators.py` | 指標計算（RSI/ATR/ADX等。素朴なループ実装と小数6桁まで一致を検証済み） |
| `judge.py` `main.py` `scan.py` | Phase 0 の判定エンジンとCLI |
| `ai_layer.py` | Claude 審査層。**モメンタム戦略では使いません**（機械的ルールにAIを挟むと再現性が失われる） |
